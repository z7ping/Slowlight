# 数据库迁移与升级说明

## 当前实现事实

Slowlight Server 当前通过 `server/internal/config/database.go` 在启动时执行 GORM `AutoMigrate`，并在同一初始化流程中执行必要的索引、回填或兼容处理。

仓库中的 `server/migrations/*.sql` 保存部分需要显式记录的结构变更脚本，但**当前没有集成独立的版本化迁移执行器**（例如 goose / golang-migrate），也不存在一个已经投入生产使用的 `migrate up/down` CLI。

因此当前公开预览阶段的数据库升级模型是：

```text
备份 PostgreSQL
    ↓
在测试/非唯一数据副本验证新版本
    ↓
启动新版 Slowlight Server
    ↓
InitDB / AutoMigrate + 必要兼容处理
    ↓
验证同步、查询和关键数据
```

## Local → Cloud 迁移事务与重试

迁移业务数据与成功报告由同一个 PostgreSQL 事务提交；同一账号的迁移执行串行化，防止重复写入。
报告保存本地 ID 到云端 ID 的映射（不保存原始业务正文）；客户端请求超时后，使用相同快照和冲突策略重试可恢复原始映射。
已完成的旧报告如果缺失 ID 映射，服务端返回 409，阻止重复导入。需要先备份并比对云端记录。
迁移不会删除本地 SQLite；完成后仍需核对核心行为事件与关联关系。

## 数据迁移向导协议（Windows / Android）

迁移向导在 Windows 使用居中对话框、在 Android 使用全屏步骤导航，但共享同一业务状态：

1. **只读预览**：`POST /api/migration/preview` 返回八类数量、同名冲突及 `preview_version`。冲突包含云端行 ID 和更新时间，编辑/替换同名项会令预览过期。
2. **逐项选择**：每个冲突以 `entity + local_id` 标识，客户端明确提交 `conflict_choices: [{entity,local_id,policy}]`。策略：`cloud` 复用云端、`local` 将云端同名项改名备份、`both` 将本地项改为独立副本名导入。不允许静默采用本地优先。
3. **最终确认**：`POST /api/migration/execute` 提交原快照及相同 `preview_version`；提交前客户端重读本机快照并核对当前账号，服务端在写入事务内重查云端冲突及其版本。变化返回 409，用户必须重新预览。
4. **执行与回执**：服务器保留原子写入、同源指纹防重和 ID 映射回执；客户端再验证回执并以本机事务回填 `server_id`。只有两层均成功才显示已完成，才允许用户主动切换云端模式。
5. **超时、崩溃及未确认结果**：`POST /api/migration/recover` 用上次**相同原始提交快照**的指纹查询已提交回执，只读取不插入。查到回执后验证并恢复本机映射；查不到时仍显示未确认，不重新导入。迁移历史中的“核对并恢复”也只调用该只读端点。
6. **隐私**：完成映射并登记成功后，清除本机迁移留痕中的原始快照；失败记录暂留恢复所需快照，原始本地数据库不会被删除。服务端审计以最小必要映射/摘要为主。

旧客户端不附带 `preview_version` 时，服务端仍兼容全局 `conflict_policy` 请求以避免协议直接中断；正式新版客户端始终使用逐项策略。更改云端数据、同源不同快照、旧成功报告缺映射均应拒绝自动覆盖或重传。

设计细节与 Windows/Android 验收矩阵的权威版本保存在私有 `product-internal`；此处仅记工程协议，不复制私有原型。

## AutoMigrate 的边界

GORM `AutoMigrate` 适合处理当前阶段的大部分兼容性新增，但不能被理解为完整的生产数据库变更系统。

特别需要谨慎处理：

- 列重命名或删除；
- 可能丢失数据的类型变更；
- 唯一索引或外键语义变化；
- 大表回填；
- 需要可控停机窗口的迁移；
- 需要明确回滚步骤的不可逆变更。

此类变更不能只依赖“服务启动成功”判断迁移安全。

## 升级前建议

### 1. 备份

重要数据升级前先创建 PostgreSQL 备份，并确认备份可以恢复。

示例：

```bash
pg_dump -Fc slowlight > slowlight-backup.dump
```

示例只表示 PostgreSQL 的一种备份方式，真实部署需要根据容器、托管数据库、账号和备份策略调整。

### 2. 先验证再覆盖

公开预览阶段尤其建议：

- 不在唯一数据副本上第一次验证新版本；
- 数据结构变化先在副本或测试环境运行；
- 升级后检查任务、习惯、Session、BehaviorEvent、同步游标和删除语义；
- 多设备环境继续检查删除记录不会被旧设备重新复活。

### 3. 不假设存在自动回滚

当前仓库没有通用的数据库 `down` 迁移机制。涉及不可逆结构变化时，PR / Release Notes 应明确：

- 升级前置条件；
- 数据备份要求；
- 是否需要手工 SQL；
- 失败后如何恢复数据库和应用版本。

## 新增数据库变更时

贡献者应遵循：

1. 优先设计为向后兼容、幂等的变更；
2. 同步更新 GORM Model / 初始化逻辑；
3. 如果需要显式 SQL，在 `server/migrations/` 中保留可审查的脚本；
4. 补充相关测试，尤其关注默认值、唯一约束、时间语义和历史数据；
5. 不删除旧字段或数据，除非已经明确迁移与恢复方案；
6. 不能把仅在空数据库验证过的变化描述为已经完成生产数据升级验证。

## 后续方向

在进入更稳定的公开发行阶段前，可以根据真实部署复杂度评估是否引入版本化数据库迁移执行器。若引入，目标应是：

- 明确记录已执行版本；
- 可在 CI / 部署流程验证迁移完整性；
- 对不可逆变更提供显式升级说明；
- 与当前 GORM Model 和数据一致性测试保持单一事实来源，不形成两套互相漂移的 schema 描述。

在正式实现这套机制之前，文档不会假设 `goose`、`golang-migrate` 或其它工具已经是 Slowlight 的运行依赖。
